# AI 여행 일정 플래너 — PRD (Product Requirements Document)

- 작성일: 2026-07-06 (최종 수정: 2026-07-15)
- 문서 버전: v2.6 (저장된 일정 재조정에도 "미리보기 → 명시적 저장" 적용)
- 관련 문서: 5W1H_AI여행플래너.md

## 1. 개요

여행 일정을 직접 짜는 데 드는 시간과 고민을 줄여주는 AI 기반 여행 일정 플래너다. 사용자가 목적지/기간/예산/취향을 입력하면 AI가 지리적으로 합리적인 일자별 동선을 생성하고, 사용자가 특정 날짜의 활동 순서를 드래그로 수정하면 그 날짜만 AI가 재계산하고 나머지 날짜는 원본 그대로 유지한다.

## 2. 배경 및 문제 정의

- 여행지에 대한 정보가 많을수록 일정을 스스로 짜는 데 드는 시간과 고민이 커진다.
- 사람이 직접 짜면 이동 동선이 비효율적이거나 시간대가 겹치는 실수가 생기기 쉽다.
- 기존 도구는 한 번 만들어주고 끝이거나, 수정하려면 전체를 처음부터 다시 생성해야 해서 사용자가 마음에 들어했던 다른 날짜의 일정까지 함께 사라지는 문제가 있다. 본 서비스는 "일부만 수정 → 나머지는 유지"라는 부분 재생성으로 이 문제를 해결한다.

## 3. 목표 / 비목표

### 3.1 목표

- 일정 생성 → 드래그로 순서 수정 → AI가 변경 반영해 재조정(일자 단위 부분 재생성) → 저장까지의 핵심 루프를 10일 내 완성
- 사용자별 로그인 및 여행 일정 저장/재열람
- 관리자가 일정 품질(동선 이상 케이스)을 모니터링하고 프롬프트를 관리
- 필수 구현 요소(인증/인가, DB 스키마, 화면 4개 이상, AI 판정 연동, 기본 API 문서화) 전체 구현
- 개발 기간 10일, 실비용 $10 이내 완료

### 3.2 비목표 (이번 스프린트 제외)

- CI/CD 파이프라인 — 수동 배포로 충분
- 자동화 테스트 스위트 — 핵심 로직 1~2건만 수동 검증
- 비동기 큐(BullMQ 등) — AI 응답 대기는 로딩 UI로 대응
- 별도 캐시 레이어(Redis 등) — Supabase 단일 저장소로 충분, 인프라 단순화를 위해 제외
- 소셜 로그인, 비밀번호 재설정, 이메일 인증 — 자체 회원가입/로그인만 지원
- 다국어 지원
- 실시간 항공/숙박 예약 연동, 결제, 협업(공동 편집) 기능

## 4. 대상 사용자 및 시나리오

**대상 사용자**

- 여행 일정을 직접 짜는 게 번거롭거나 시간이 부족한 개인/그룹 여행자 (`user`)
- 목적지는 정했지만 동선이나 세부 일정 구성에 자신 없는 사용자
- 일정 품질과 프롬프트를 관리하는 운영자 (`admin`)

**목적지 범위**: 제한 없음 (국내/해외 모두 지원)

**핵심 시나리오**: 부산 2박 3일 일정을 받았는데 둘째 날 순서가 마음에 안 들어서 오전/오후 활동을 드래그로 바꾸면, AI가 그 순서에 맞춰 이동 동선과 시간대를 자연스럽게 다시 짜준다. 나머지 날짜는 그대로 유지된다. 만약 그 순서가 지리적으로 비효율적이면 일정표 화면에 경고 배지와 안내 문구가 함께 표시된다.

## 5. 사용자 흐름

일반 사용자: 로그인/회원가입 → 일정 생성 폼 작성(목적지/기간/예산/취향) → AI 호출(로딩) → 일정표 화면에 결과 표시(일자별 카드, 드래그 가능, 이상 동선 배지 표시) → 카드 순서 드래그 → "재조정" 요청 → 변경된 날짜만 재계산, 다른 날짜는 유지 → 재계산 결과가 비효율적이면 경고+tips 노출, "동선 최적화 재요청" 선택 가능(반복) → 저장 → Supabase에 저장 → 저장한 여행 목록에서 재열람.

관리자: 로그인(admin) → 품질 모니터링(이상 동선 플래그 목록) / 인기 목적지 통계 / 프롬프트 템플릿 관리.

## 6. 기능 요구사항

### 6.1 인증/인가

- 이메일/비밀번호 기반 회원가입 및 로그인
- JWT 기반 인증, 역할(`user`/`admin`) 기반 인가
- 토큰 관리: JWT를 클라이언트 sessionStorage에 저장. 서버는 별도 토큰 테이블 없이 access token 자체(짧은 만료시간, 예: 30분~1시간)로만 인증하며, 로그아웃은 클라이언트에서 sessionStorage를 비우는 방식으로 처리(서버 측 강제 무효화는 지원하지 않음 — 탈취된 토큰은 만료 전까지 유효할 수 있다는 점을 알려진 트레이드오프로 명시)

### 6.2 일정 생성 및 저장

#### 6.2.1 최초 생성 (임시)

- 목적지, 여행 기간, 예산, 활동 시간대(시작/종료), 동반인, 취향(다중 선택)을 입력받아 AI가 일자별 동선을 생성
- 생성 결과는 클라이언트 sessionStorage에 임시 저장됨 (DB에는 저장하지 않음)
- 사용자는 이 시점에서 일정을 조정(드래그 순서 변경, 일자별 활동 교체, 전체 재생성)할 수 있음

#### 6.2.2 저장

**핵심 원칙(v2.6)**: AI 호출(생성/재조정/일자별 교체/전체 재생성)과 DB 반영은 항상 분리되어 있다. 어떤 조정 액션이든 AI 호출 결과는 즉시 화면에 반영되지만 그 자체로는 DB에 저장되지 않으며, 사용자가 화면의 "저장" 버튼을 명시적으로 클릭해야만 그 시점 화면에 표시된 내용이 DB에 반영된다. 이 원칙은 임시(저장 전) 일정뿐 아니라 **저장한 여행 목록에서 다시 연 일정(저장 후 재열람, 6.4)에도 동일하게 적용된다** — v2.5까지는 저장 후 재열람한 일정의 조정이 즉시 DB에 반영됐으나, v2.6부터는 저장 전 임시 일정과 완전히 동일한 "미리보기 → 저장" 흐름을 따른다.

- **최초 생성 후 저장** (trip_id 없는 임시 상태): "저장" 클릭 시 새로운 trip_id 생성, revision=1로 시작. 이후 "여행 목록"에서 조회 가능.
- **저장된 일정 재열람 후 저장** (6.4, trip_id 있음): 재조정/일자별 활동 교체로 발생한 변경은 **같은 trip_id를 유지한 채** "저장" 클릭 시점에 한 번에 반영되고 revision이 1 증가한다(그 사이 여러 day를 조정했어도 저장은 한 번에, revision도 1만 증가). 저장하지 않고 화면을 벗어나면 DB의 기존 내용은 전혀 바뀌지 않는다 — "현재의 저장방식"(같은 trip_id 갱신)은 그대로 유지하되 시점만 미룬다.
- **전체 재생성 후 저장** (임시 상태든 저장된 상태든): 항상 **새로운 trip_id**를 생성한다("현재의 저장방식" 그대로 — 6.2.3 참고). 저장된 일정에서 전체 재생성을 미리보기만 하고 저장하지 않으면 원본 trip은 전혀 바뀌지 않는다.

#### 6.2.3 전체 재생성

- 임시 일정 또는 저장된 일정 모두 "재생성" 버튼으로 AI가 완전히 새로운 일정을 다시 만들어주는 것을 미리볼 수 있다. 입력값(목적지, 기간, 예산, 활동시간, 동반인, 취향)은 유지하고 AI만 새로 호출(캐시 항상 무시).
- 결과는 화면에 즉시 반영되지만 **DB에는 저장되지 않는다**(임시/저장된 상태 공통). 마음에 들면 "저장" 버튼을 눌러야 비로소 반영되며, 이때 **항상 새로운 trip_id가 생성**된다(기존 trip은 그대로 유지 — 사용자는 v1/v2를 여행 목록에서 비교 가능, 6.2.2의 "현재의 저장방식" 원칙).

### 6.3 일정표 편집 및 재조정 (일자 단위 부분 재생성 — 확정)

#### 6.3.1 활동 순서 변경

- 일정표 화면에서 같은 날짜 내 활동 순서를 드래그로 변경 후 "재조정 요청" 클릭
- 변경된 날짜(day)와 새 활동 순서만 AI에 전달하고 다른 날짜는 절대 수정하지 않고 원본 그대로 반환하도록 프롬프트로 강제
- 응답 검증 단계에서 요청하지 않은 day의 activities가 원본과 다르면 프롬프트 위반으로 간주해 재시도
- **"재조정 요청"은 AI 호출 + 미리보기 반환일 뿐, 그 자체로 DB에 반영되지 않는다**(임시 상태든 저장된 상태든 공통). 여러 day를 연달아 재조정 요청해도 전부 화면(로컬 상태)에만 누적 반영되고, "저장" 버튼을 눌러야 한 번에 DB에 반영된다.
  - 임시 일정에서 저장: 새로운 trip_id 생성(6.2.2)
  - 저장된 일정에서 저장: **같은 trip_id를 유지**한 채 갱신, revision 1 증가, 스냅샷 보관(6.2.2)

#### 6.3.2 일자별 활동 교체

- 일정표 화면에서 특정 day의 "활동 재생성" 버튼으로 그 날의 활동 목록 전체를 새로 생성 요청
- 프롬프트에 **다른 day들의 모든 활동들을 포함**하여 중복 방지 (예: "Day 2를 새로 생성하되, Day 1과 Day 3의 다음 장소들과 겹치지 말 것: ...") — 다른 day 정보는 현재 화면(로컬 상태)에 있는 값을 그대로 사용한다(아직 저장 전인 다른 day의 조정 내용도 반영됨)
- "활동 재생성" 역시 AI 호출 + 미리보기 반환이며 DB에는 반영되지 않는다. "저장" 버튼을 눌러야 반영되는 것은 6.3.1과 동일(임시→새 trip_id, 저장된 일정→같은 trip_id 갱신)
- 응답 검증: 요청하지 않은 day는 변경 불가 (6.3.1과 동일)

### 6.4 저장한 여행 목록

- 완성한 일정을 저장하고 목록에서 조회, 다시 열어 이어서 수정 가능
- "이어서 수정"도 6.2.2/6.3의 "미리보기 → 저장" 원칙을 그대로 따른다 — 다시 연 일정을 조정만 하고 저장하지 않은 채 목록으로 돌아가면 DB의 원래 내용은 바뀌지 않는다.

### 6.5 AI 판정 로직 및 결과 노출

- 재조정된 동선이 지리적으로 합리적인지 판정(이동 거리/순서 기반 룰 체크 + AI 자연어 사유)
- 판정 결과는 구조화된 필드(route_warning: flagged, reason)로 반환되어 두 곳에서 소비된다.
  - 사용자 화면: 해당 day 카드에 경고 배지 + tips에 자연어 설명 노출. 활동 순서 자체는 사용자가 정한 대로 유지하되, 이동 소요시간에 현실을 반영하고 "동선 최적화 재요청" 버튼으로 재조정 기능과 연결
  - 관리자 화면: flagged=true인 trip/day를 품질 모니터링 목록에 집계해 노출, 반복 패턴을 파악해 프롬프트 개선에 활용
- 판정 결과를 관리자 전용 정보로 숨기지 않고 사용자에게도 즉시 안내해 판정 로직과 재조정 기능이 실제 사용자 액션으로 연결되도록 설계

### 6.6 관리자 기능

- 생성된 일정 중 동선 이상 케이스 모니터링(6.5의 flagged 목록, Supabase 쿼리로 조회)
- 목적지별 생성 건수 등 인기 목적지 통계 확인(Supabase SQL 집계 쿼리: `GROUP BY destination`)
- AI 프롬프트 템플릿 조회/수정/버전 관리
- 일반 사용자(user) 계정으로는 관리자 API/화면 접근 불가(403)

### 6.7 API 문서화

- 인증, 일정 생성/조회/재조정, 관리자 통계·모니터링·프롬프트 관리 API에 대한 OpenAPI(Swagger) 문서 제공
- PRD 자체에도 9절 API 계약으로 요청/응답 JSON을 명시(문서화 누락 방지)

### 6.8 AI 응답 캐싱 (비용 절감, Supabase 테이블 기반)

- 별도 캐시 서버 없이, Supabase에 `ai_response_cache` 테이블을 두어 동일 조건(목적지+기간+예산+취향 해시)의 최초 생성 요청에 대한 AI 응답을 저장
- 동일 조건 재요청 시 캐시 테이블 조회 결과를 우선 반환해 AI API 호출 횟수와 비용을 절감
- 캐시는 재조정(부분 수정) 요청에는 적용하지 않음(사용자별로 결과가 달라지므로 최초 생성 단계에서만 활용)

## 7. 비기능 요구사항

- 비용: 개발 기간 중 실비용 $10 이내 (Supabase는 무료 티어, AI API 호출만 실비용 — 저비용 모델 + Supabase 캐시 테이블(6.8)로 관리)
- 일정: 개발 기간 10일 내 완료
- 보안: 비밀번호 해시 저장, JWT 만료/갱신 처리, 관리자 화면은 admin 역할만 접근 가능
- 성능: AI 응답 대기 중 로딩 상태 표시, 캐시 가능한 요청은 Supabase 캐시 테이블 조회로 응답 속도/비용 개선
- 확장성 고려하지 않음: 포트폴리오/학습 목적의 단일 인스턴스 운영 전제

## 8. 데이터 스펙

### 8.1 최초 생성 입력

- destination(텍스트, 제한 없음, 필수)
- start_date, end_date(YYYY-MM-DD, 필수)
- budget_level(자유 텍스트, 최대 30자, 필수)
- activity_time_start, activity_time_end(HH:MM, 24시간제, 필수) — 예: "09:00", "20:00"
- companion(문자열 enum, 필수): 혼자 | 친구 | 연인/배우자 | 아이 | 부모님 | 기타
- preferences(문자열 배열, 다중 선택, 필수): 체험&액티비티, 자연, 유명 관광지, 힐링, 문화&예술&역사, 쇼핑, 먹방, SNS 핫플레이스

### 8.2 재조정 요청 입력

**임시(저장 전) 조정 요청 — 공통 바디**: 서버가 DB를 조회하지 않는 stateless 엔드포인트이므로, 서버가 계산에 필요한 컨텍스트를 매 요청마다 프론트가 전부 담아 보내야 한다. 바디 = 8.1 입력 필드 전체(destination/start_date/end_date/budget_level/activity_time_start/activity_time_end/companion/preferences) + summary + days[](8.3 출력의 day 배열, 프론트가 sessionStorage에 들고 있는 현재 임시 일정 그대로). 여기에 액션별로 아래 필드가 추가된다.

- PATCH /api/trips/reorder 추가 필드: day(재조정할 일차), new_activity_order(드래그 후 activity id 배열)
- PATCH /api/trips/regenerate-day 추가 필드: day(교체할 일차) — 다른 day 활동 목록(중복 방지용)은 별도로 보낼 필요 없이 함께 보낸 days[]에서 서버가 직접 추출해 사용
- POST /api/trips/regenerate 추가 필드: 없음(days[]는 무시하고 8.1 입력값으로 AI를 새로 호출)

세 엔드포인트 모두 응답은 8.3 스키마(trip_id, meta.revision 제외)이며, 대상 day만 재계산하고 나머지 day는 요청받은 그대로 돌려준다 — 서버가 대상 day 외에는 아예 읽지 않고 relay만 하므로 핵심 불변 규칙(변경 요청한 day 외 수정 금지)이 구조적으로 보장된다.

**저장 후(trip_id 기반) 조정 요청 — 미리보기(v2.6 변경)**: trip_id는 URL 경로 파라미터. destination/활동시간대 등 정적 입력값은 서버가 trip_id로 DB에서 직접 조회하므로 별도로 보낼 필요 없다. 다만 같은 세션에서 다른 day를 먼저 미리보기했을 수 있으므로(아직 저장 전) 그 상태를 잃지 않도록 현재 화면의 days[] 전체도 함께 보낸다.

- PATCH /api/trips/{trip_id}/reorder 요청: day(재조정할 일차), new_activity_order(드래그 후 activity id 배열), days[](현재 화면에 표시된 로컬 일정 전체)
- PATCH /api/trips/{trip_id}/regenerate-day 요청: day(교체할 일차), days[](현재 화면의 로컬 일정 전체 — 다른 day 정보는 여기서 서버가 추출)
- POST /api/trips/{trip_id}/regenerate 요청: `{}`(원본 trip에 저장된 입력값을 서버가 DB에서 조회)

세 엔드포인트 모두 **DB에는 전혀 반영되지 않는다**(미리보기, PRD 6.2.2). reorder/regenerate-day는 trip_id·현재 저장된 revision을 그대로 유지한 채 대상 day만 재계산해 응답하고 나머지는 요청받은 그대로 relay한다. 전체 재생성(regenerate)은 저장 전까지 어떤 trip에도 속하지 않는 완전히 새로운 내용이므로 trip_id/meta.revision이 없는 형태(8.3 "주의" 참고)로 응답한다.

**저장 후(trip_id 기반) 커밋(저장) 요청 — 신규(v2.6)**

- POST /api/trips/{trip_id}/save — day 단위 미리보기(reorder/regenerate-day)로 누적된 변경을 같은 trip_id에 반영. 요청: days[](현재 화면에 표시된 최종 일정 전체)
- POST /api/trips/{trip_id}/regenerate/save — 전체 재생성 미리보기를 새로운 trip으로 반영. 요청: summary, days[](미리보기 응답 그대로)

### 8.3 출력 데이터 스펙 (JSON)

```json
{
  "trip_id": "trip_abc123",
  "destination": "부산",
  "duration_days": 3,
  "summary": "부산 2박 3일 힐링+먹방 일정",
  "days": [
    {
      "day": 1,
      "theme": "도착 및 시내 탐방",
      "activities": [
        {
          "id": "d1-a1",
          "time": "09:00",
          "title": "해운대 도착",
          "description": "...",
          "category": "유명 관광지",
          "duration_minutes": 90,
          "location": "해운대구",
          "estimated_cost": 0,
          "tips": null
        }
      ],
      "last_modified": false,
      "route_warning": { "flagged": false, "reason": null }
    }
  ],
  "meta": { "generated_at": "2026-07-10T10:00:00Z", "revision": 2 }
}
```

- days[].activities[].time: 활동 시작 시간. 사용자 입력 activity_time_start/end 범위 내에서 AI가 결정함
- days[].last_modified: 이번 재조정에서 실제로 재계산된 날짜인지(프론트 "변경됨" 뱃지용)
- days[].route_warning: AI 판정 결과 — 사용자 화면 경고 배지 및 관리자 모니터링 목록에 공통으로 사용
- meta.revision: 재조정 반영 횟수

**주의(v2.6 갱신)**:
- `trip_id`/`meta.revision`이 **없는** 응답: POST /api/trips/generate, PATCH /api/trips/reorder, PATCH /api/trips/regenerate-day, POST /api/trips/regenerate(모두 trip_id 없는 경로, 저장 전 임시), 그리고 POST /api/trips/{trip_id}/regenerate(전체 재생성 미리보기 — trip_id 경로가 있어도 저장 전까지는 새 내용이 아직 어떤 trip에도 속하지 않으므로 trip_id를 반환하지 않는다).
- `trip_id`/`meta.revision`이 **있는** 응답: POST /api/trips(저장), PATCH /api/trips/{trip_id}/reorder·regenerate-day(미리보기 — trip_id/revision은 DB에 저장된 현재 값 그대로이며 아직 반영되지 않았음을 뜻함), POST /api/trips/{trip_id}/save, POST /api/trips/{trip_id}/regenerate/save(둘 다 커밋 결과이므로 반영된 revision을 반환).

## 9. API 계약

- POST /api/auth/signup, POST /api/auth/login, POST /api/auth/logout
- POST /api/trips/generate — 임시 생성(AI 호출). 요청: 8.1 스키마(`{ "destination": "부산", "start_date": "2026-07-10", "end_date": "2026-07-12", "budget_level": "중상", "activity_time_start": "09:00", "activity_time_end": "20:00", "companion": "친구", "preferences": ["힐링", "먹방"] }`) / 응답(200): 8.3 스키마(trip_id, revision 제외). 동일 조건이 `ai_response_cache`에 있으면 캐시 결과 반환
- POST /api/trips/regenerate — 전체 재생성(임시). 요청: 8.1 스키마와 동일(입력값 그대로 재사용, 함께 보내는 days[]는 무시) / 응답(200): 8.3 스키마(trip_id, revision 제외). AI 호출, DB 저장 X, 캐시 항상 무시
- PATCH /api/trips/reorder — 활동 순서 변경(임시). 요청: 8.2 참고(8.1 입력 전체 + summary + days[] + day + new_activity_order) / 응답(200): 8.3 스키마(trip_id, revision 제외, 대상 day만 재계산·나머지는 받은 그대로 반환). AI 호출, DB 저장 X
- PATCH /api/trips/regenerate-day — 일자별 활동 교체(임시). 요청: 8.2 참고(8.1 입력 전체 + summary + days[] + day) / 응답(200): 8.3 스키마(trip_id, revision 제외, 대상 day만 새 활동으로 교체·나머지는 받은 그대로 반환). AI 호출, DB 저장 X, 다른 day 정보는 요청에 포함된 days[]에서 서버가 추출
- POST /api/trips — 저장. 요청: 8.1 입력 전체 + summary + days[](프론트에서 조정한 최종 임시 일정) / 응답(200): 8.3 스키마 전체(trip_id 생성, revision=1). AI를 다시 호출하지 않고 전달받은 days[]를 그대로 저장하되, day 범위·activity 필수 필드는 서버가 구조 검증
- POST /api/trips/{trip_id}/regenerate — 전체 재생성 **미리보기**(저장된 trip 대상, AI 호출, DB 미반영, v2.6). 요청: `{}`(원본 trip에 저장된 입력값을 서버가 DB에서 조회해 그대로 사용) / 응답(200): 8.3 스키마에서 trip_id/meta.revision 제외(저장 전까지는 어떤 trip에도 속하지 않음). 캐시 항상 무시
- PATCH /api/trips/{trip_id}/reorder — 활동 순서 변경 **미리보기**(AI 호출, DB 미반영, v2.6). 요청: `{ "day": 2, "new_activity_order": ["d2-a3", "d2-a1", "d2-a2"], "days": [...] }`(days는 현재 화면의 로컬 일정 전체) / 응답(200): 8.3 스키마 전체(trip_id 동일, revision은 DB의 현재 값 그대로 — 아직 미반영, 대상 day만 재계산·나머지는 요청받은 그대로 반환)
- PATCH /api/trips/{trip_id}/regenerate-day — 일자별 활동 교체 **미리보기**(AI 호출, DB 미반영, v2.6). 요청: `{ "day": 2, "days": [...] }`(다른 day 정보는 함께 보낸 days[]에서 서버가 추출) / 응답(200): 위와 동일 패턴(trip_id 동일, revision 미반영, 대상 day만 새 활동으로 교체)
- POST /api/trips/{trip_id}/save — (신규, v2.6) day 단위 미리보기(reorder/regenerate-day) 커밋. 요청: `{ "days": [...] }`(현재 화면의 최종 일정 전체) / 응답(200): 8.3 스키마 전체(같은 trip_id, revision 1 증가 — 여러 day를 모아 저장했어도 1만 증가, changed_day_number는 null로 스냅샷 기록)
- POST /api/trips/{trip_id}/regenerate/save — (신규, v2.6) 전체 재생성 미리보기 커밋. 요청: `{ "summary": "...", "days": [...] }`(미리보기 응답 그대로) / 응답(200): 8.3 스키마 전체(새로운 trip_id, revision=1). 원본 trip은 저장 목록에 그대로 유지
- GET /api/trips — 내 저장 목록(최신순)
- GET /api/trips/{trip_id} — 저장된 일정 상세
- GET /api/admin/flagged-trips — 이상 동선 플래그 목록(admin 전용)
- GET /api/admin/stats/destinations — 인기 목적지 통계(admin 전용)
- GET/PUT /api/admin/prompt-templates, /api/admin/prompt-templates/{id} — 프롬프트 템플릿 조회/수정(admin 전용)
- 에러 응답 형식: `{ "error": "VALIDATION_ERROR" | "GENERATION_FAILED" | "AUTH_ERROR" | "FORBIDDEN" | "STORAGE_ERROR", "message": "..." }`

## 10. 에러 처리 및 엣지케이스

- AI 호출 실패/파싱 실패 → 구분해서 1회 재시도, duration_days 비례 동적 max_tokens/타임아웃 적용
- 재조정 요청의 day가 존재하지 않는 범위 → 400 VALIDATION_ERROR
- 재조정 결과에서 요청하지 않은 날짜가 실수로 바뀐 경우 → 응답 검증 단계에서 원본과 비교, 다르면 파싱 실패로 간주하고 재시도
- Supabase 연결 실패 → 503 + STORAGE_ERROR, AI 호출 실패와 별도로 로깅
- AI 응답 캐시(Supabase `ai_response_cache`) 조회 실패 → 캐시를 건너뛰고 AI를 직접 호출하는 폴백 처리(서비스 중단 없이 비용 절감 효과만 저하)
- 미인증 사용자가 저장 시도 → 401 AUTH_ERROR
- 일반 사용자가 관리자 API 접근 시도 → 403 FORBIDDEN
- 동시 편집 충돌 → 이번 범위에서는 마지막 저장이 덮어쓰는 방식으로 단순 처리(락 없음, 비목표로 명시)

- 저장 버튼을 누르기 전까지는 위 조정을 몇 번 반복해도 DB(trips/itinerary_days/itinerary_activities)에 아무 행도 생기지 않는지 확인(새로고침/이탈 시 임시 일정이 사라져도 정상)

- 저장된 일정을 다시 열어 day를 2회 이상 재조정/활동 재생성해도 "저장" 버튼을 누르기 전까지는 DB(itinerary_days/itinerary_activities/trips.revision)가 전혀 바뀌지 않는지 확인(미리보기만 로컬에 누적) → "저장" 클릭 시 같은 trip_id를 유지한 채 한 번에 반영되고 revision이 1만 증가하는지 확인
- 전체 재생성: "이 일정 전체 재생성" 버튼 → 미리보기 표시(DB 미반영) → "저장" 클릭 시에만 새로운 trip_id 생성, 기존 trip은 저장 목록 유지 확인. 미리보기 후 저장하지 않고 벗어나면 원본 trip이 전혀 바뀌지 않았는지 확인
- 일자별 활동 교체: day별 "활동 재생성" 버튼 → 미리보기(DB 미반영) → 저장 시 해당 day만 새 활동으로 교체, 다른 day는 유지, 중복 방지 확인 (다른 day 활동과 겹치지 않는지)
- AI가 동선 이상을 판정하면 해당 day에 사용자 화면 경고 배지와 관리자 품질 모니터링 화면 플래그가 동일한 판정 데이터로 함께 노출되는지 확인
- 저장 → 저장한 여행 목록 조회 → 상세 재열람까지 동작, 같은 조건의 v1/v2 비교 가능
- 관리자 계정으로 품질 모니터링/인기 목적지 통계/프롬프트 템플릿 관리 3개 화면 모두 접근·기본 동작 확인, 일반 사용자 계정은 403으로 차단되는지 확인
- Supabase 재배포/재시작 후에도 저장된 데이터가 유지되는지 확인
- AI 응답 캐시(Supabase `ai_response_cache`) 적용 확인(동일 조건 재요청 시 캐시 히트로 AI 호출 절감 확인), 재생성 요청은 캐시 무시 확인
- 모든 API 엔드포인트가 9절 계약대로 Swagger 문서에 반영되어 있는지 확인
- 프론트/백엔드 모두 배포되어 URL로 접근 가능

## 15. 결정 로그

- Redis 제외, Supabase 단일 저장소로 통합: 필수 구현 요소에서 Redis를 제외하기로 함에 따라, AI 응답 캐싱은 Supabase `ai_response_cache` 테이블로, 인기 목적지 통계는 Supabase SQL 집계 쿼리로 각각 대체. 근거: 별도 캐시 인프라 없이도 요구사항을 충족할 수 있어 인프라 구성과 배포 복잡도를 낮춤(10일·$10 제약에 유리)
- 토큰은 DB 테이블 대신 클라이언트 sessionStorage에서 관리: 서버 측 refresh_tokens 테이블을 두지 않고, 짧은 만료의 access token만 발급, 로그아웃은 클라이언트에서 토큰을 삭제하는 방식으로 단순화. 근거: 구현 복잡도를 낮추고 스코프를 단순화하기 위한 선택이며, 그 대가로 탈취된 토큰에 대한 서버 측 강제 무효화는 지원하지 않는다는 점을 감수함(포트폴리오 스코프에서는 허용 가능한 트레이드오프로 판단)
- 재조정 시 전체 재생성 대신 부분 수정: 변경 날짜만 재계산, 나머지는 원본 유지, 응답 검증으로 위반 감지. 근거: 사용자가 마음에 들어한 다른 날짜까지 사라지는 문제 방지
- AI 판정 결과를 관리자 전용이 아닌 사용자에게도 노출: route_warning 필드를 사용자 배지/tips와 관리자 모니터링에 공통 사용. 근거: 판정 결과를 숨기면 사용자는 비효율적인 동선을 그대로 따르게 됨. 노출 시 재조정 기능과 자연스럽게 연결되고, 관리자는 집계된 패턴으로 프롬프트를 개선할 수 있어 양쪽 다 이득
- 기술 스택 확정(v2.2): 프론트 React+MUI+Vite+dnd-kit, 백엔드 NestJS+TypeORM, AI Google Gemini API, 지오코딩 OpenStreetMap Nominatim(+Haversine 직선거리), 배포 Vercel(FE)/Render(BE). 근거: Gemini는 보유 API 키 활용, Nominatim은 무료+국내/해외 목적지 모두 지원해 $10 예산과 목적지 범위 제한 없음 조건을 동시에 충족(Kakao는 해외 미지원, Google Maps는 유료라 제외)
- 활동 시간대, 동반인, 취향 enum 추가(v2.3): 최초 생성 입력에 activity_time_start/end, companion enum, preferences enum 명시 추가. 근거: AI가 더 맥락 있는 일정을 생성할 수 있고, 사용자별 맞춤형 추천이 가능해짐. 캐시 키에 이 필드들도 포함되어 중복 요청 시 효율성 향상. Phase 2 일정을 1일 연장해도 핵심 기능(부분 재조정)에 영향 없음
- 전체 재생성 기능 추가(v2.4): POST /api/trips/{id}/regenerate 엔드포인트 추가. 입력값(목적지/기간/예산/활동시간/동반인/취향)은 유지하고 AI만 재호출, 캐시 무시. 결과: 새로운 trip_id 생성. 근거: 사용자가 일정 전체를 다시 생성하고 싶을 때 필요. 기존 trip은 저장 목록에 유지되어 비교 가능
- 일자별 활동 교체 기능 추가(v2.4): PATCH /api/trips/{id}/regenerate-day 엔드포인트 추가. 특정 day의 활동 목록을 완전히 새로 생성하되, 다른 day의 활동들을 프롬프트에 포함해 중복 방지. 같은 trip_id 유지, revision 증가. 근거: 부분 재조정(순서 변경)과 일자별 활동 교체(활동 자체 교체)는 다른 기능이며, 사용자는 마음에 안 드는 day만 재생성 가능. 다른 day 정보를 프롬프트에 포함해 지리적 중복 방지
- 목적지 범위 제한 없음: 국내/해외 모두 지원. 근거: 별도 제약 사유가 없어 확장성 있게 설계
- 자동 저장 → 명시적 저장으로 전환(v2.5): 기존에는 최초 생성과 모든 조정(재조정/일자별 교체/전체 재생성)이 즉시 DB에 반영되는 자동 저장 방식이었으나, 사용자가 마음에 들지 않아 시행착오처럼 시도한 결과까지 DB와 저장 목록에 쌓이는 문제가 있어 "생성 → 임시 조회(sessionStorage) → 조정/재생성(모두 임시) → 저장 버튼 클릭 → 저장" 흐름으로 변경. 저장 전 조정 3종(POST /trips/regenerate, PATCH /trips/reorder, PATCH /trips/regenerate-day)은 trip_id 없는 경로로 분리해 DB에 전혀 접근하지 않는 stateless 엔드포인트로 만들고, 서버가 상태를 들고 있지 않으므로 매 요청마다 프론트가 8.1 입력값+현재 임시 days[] 전체를 함께 보내야 함(8.2). (v2.5 당시에는 저장한 여행 목록에서 다시 연 trip에 대한 조정은 기존 trip_id 기반 엔드포인트로 즉시 DB 반영을 유지했으나, v2.6에서 아래와 같이 재검토됨)
- 저장된 일정 재열람 시에도 "미리보기 → 명시적 저장" 적용(v2.6): 프론트 구현 후 실사용해보니, 저장한 일정을 다시 열어 드래그 재조정이나 활동 재생성을 할 때 "저장" 버튼이 없어 다른 화면과 UX가 불일치하고, 클릭 한 번(드래그+재조정 요청)만으로 이미 저장된 데이터가 즉시 바뀌어버리는 것이 뜻하지 않은 변경 위험으로 느껴짐. 이에 저장 전/후를 가리지 않고 "AI 호출과 화면 반영은 즉시, DB 반영은 저장 버튼을 눌러야만"이라는 원칙으로 통일. 다만 저장 시 **실제로 반영되는 대상은 기존 동작을 그대로 유지**한다("현재의 저장방식 적용") — day 단위 조정(reorder/regenerate-day)의 저장 결과는 여전히 같은 trip_id를 갱신(revision +1)하고, 전체 재생성의 저장 결과는 여전히 새로운 trip_id를 만든다(원본 유지, v1/v2 비교 가능). 이를 위해 PATCH /trips/{trip_id}/reorder·regenerate-day와 POST /trips/{trip_id}/regenerate를 미리보기 전용(DB 미반영)으로 바꾸고, 커밋 전용 엔드포인트 2종(POST /trips/{trip_id}/save, POST /trips/{trip_id}/regenerate/save)을 신설. 근거: 저장 전/후 화면의 상호작용 모델을 하나로 통일해 사용자가 "이 조정이 지금 바로 반영되는지"를 매번 다르게 학습할 필요가 없게 하고, 저장된 일정에 대한 의도치 않은 즉시 변경(실수로 인한 덮어쓰기)을 방지

## 16. 오픈 이슈
